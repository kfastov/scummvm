# 0058 — `CDBGetValueEx` дочитан: свойства разбирает сама среда, а не база

**Дата:** 2026-08-14
**Статус:** ✅ механизм понятен, 🔴 соответствие «номер → имя» не найдено
**Тип:** разбор чужого кода, включая отрицательный результат

## Что делает `CDBGetValueEx`

`MTB40BAS.DLL`, ordinal 144, seg15:0x0bc0. Прочитан до конца.

1. Считает индекс: `sub ax, 4000h` при номере ≤ `0x4288`, иначе `add ah, 70h`
   (это уже записано в 0057).
2. **Индекс дальше не используется.** Он кладётся в локальную переменную и в
   этой функции больше не читается — проверено по всей функции.
3. Настоящая работа идёт через таблицу описателей:

```
mov  al, byte [bp+12h]        ; выбор описателя
imul si, ax, 66h              ; шаг таблицы — 0x66 байта
les  bx, [bp-6]
les  bx, es:[bx+2]            ; указатель на таблицу
mov  ax, es:[bx+si+4]         ; дальний указатель из описателя
mov  dx, es:[bx+si+6]
...
lcall [bp-2ch]                ; вызов обработчика с объектом и номером свойства
```

То есть у каждого **класса объектов** свой обработчик свойств, и номер
передаётся ему. База сама ничего про номера не знает.

## Где эти обработчики

Поиск по всем модулям среды на плотность сравнений с номерами вида
`0x40xx..0x42xx` (`cmp ax, imm` и цепочки `sub ax, imm`) дал ровно один
выделяющийся сегмент: **`MTB40RUN.EXE` сегмент 66** — тот самый, где лежит
`builtin 140`, чтение свойства. В нём различается **73 номера**.

Важное для нас: **`0x4030` среди них нет**. Значит это свойство среда не
обрабатывает особо — оно живёт в общем хранилище, и его умолчание должно
приходить из сериализованных данных книги. Наше хранилище ведёт себя так же,
не хватает только начального наполнения.

А **`0x400f` — есть**, и по нему видно, что это за свойство:

```
push [bp-4]
lcall MTB40UTL.5      ; ax = аргумент * [ds:2ch]  — умножение на масштаб
push ax
lcall MTB40UTL.18     ; тот же масштаб
mov  [bp-4], ax
jge  дальше
neg  word [bp-4]      ; модуль
```

`MTB40UTL.5` — это `imul word [0x2c]`, то есть перевод единиц. Свойство
`0x400f` — **мера** (размер или координата), приводимая к текущим единицам и
берущаяся по модулю. Именно его обработчик из фона «Message» ставит в 12,
вычисляя размер диалога.

## Отрицательный результат: имена не из таблиц компилятора

Чтобы не повторять этот путь. В `MTB40CMP.DLL` таблицы имён лежат **не в
сегментах, а в ресурсе**: тип `0x8064`, id `0x8073`, файл `0x04af20`, длина
`0x3c20`. Внутри него две таблицы, обе разобраны:

* массив из **975 смещений** по `0x4be5e`, в порядке строк (смещения растут);
* массив из **974 пар «смещение, номер»** с `0x4af20`.

Смещения в обеих отсчитываются от начала ресурса. Таблицы **не согласуются
между собой**: при сравнении без учёта регистра совпадает 50 записей из 970, и
никакое выравнивание массива пар этого не исправляет.

Главное же — обе дают для `0x400f` имя `aboutToolBook`, а по машинному коду это
мера с переводом единиц. Значит **пространство номеров свойств — не
пространство лексем компилятора**, и искать имена в этих таблицах бесполезно.

## Куда идти дальше

1. Дочитать разбор в `MTB40RUN` сегмент 66 для тех номеров, которые книга
   действительно использует: там видно и смысл, и поле записи.
2. Для номеров без особого разбора (как `0x4030`) — найти, откуда общее
   хранилище берёт начальное значение при загрузке книги. Это и есть недостающие
   умолчания.
