# 0061 — Эталон доходит до ввода имени; движок уходит в ветку ошибки

**Дата:** 2026-08-14
**Статус:** ⚠️ расхождение локализовано
**Тип:** сверка с эталоном

## Эталон

Стенд поднят заново из снимка (`MACHINE=pc-i440fx-10.1 LOADVM=bashnya-installed
HEADLESS=1 ./3-vm.sh run bashnya`) — прежний процесс со вчерашней отладки висел
с чёрным экраном, хотя `info status` показывал `running`. Снимок экрана:
игра работает и показывает **диалог ввода имени** — «введи своё имя :», поле,
кнопки «да»/«нет» и свиток с вступительным текстом.

Значит стартовые проверки оригинал проходит и **никакого сообщения об ошибке не
показывает**.

## Что делает наш движок

Наш прогон доходит до посылки `myMessage` в фон «Message», и текст, лежащий на
стеке, — «Не найден файл». То есть движок **входит в ветку ошибки**, которой у
оригинала нет.

## Исходники подтверждают

Разжатие (0060) даёт исходный текст стартовых проверок. Он устроен так:

```
local string errorMessage
    errorMessage = "Не найден файл" && winPath & "MTB40.INI." & CRLF &
                   "Необходимо повторить установку программы."
    send myMessage errorMessage to backGround "message"
```

и рядом — соседние проверки: 256 цветов, «SMALL FONTS», «Video for Windows»,
звуковые устройства, ошибка в самом файле. Каждая проверка — свой обработчик,
условие живёт у вызывающего.

Отдельно видно, что сообщение собирается конкатенацией (`&&` и `&`), а у нас на
стеке оказался только первый кусок. Значит, помимо неверной ветки, есть и
расхождение в сборке строки.

## Трассировка в движке

Чтобы такие расхождения ловились быстро, в движок добавлены два уровня:

* `-d 3` — каждый платформенный вызов по имени;
* `-d 4` — каждый встроенный вызов по номеру.

Трасса стартового пути сейчас такая: `displayFonts`, `GlobalAlloc`/`GlobalLock`,
`AddFontResource`, `getModulePath`, `getFileVersion`, `getWinIniVar`,
`GetWindowsDirectory`, `getIniVar`, `fileExists`, `SetFileAttributes` — и сразу
сообщение. Ни одна из этих проверок не отдала «файла нет»: `getIniVar` вернул
настоящее значение из `MTB40.INI`, `fileExists` для `KNTOWER.TBC` вернул
истину. Значит условие, уводящее в ветку ошибки, вычисляется **внутри книги**, а
не в платформенном вызове.

Ещё видно, что обработчик сообщения крутит цикл: пять раз подряд ставит
`0x400f := 12` и `0x402e := ""`, читая `0x4030`, которого у нас нет.
Скорее всего именно отсутствующие умолчания свойств и портят вычисление.

## Ловушка стенда

Гость, оставленный с подключённой заглушкой GDB, может «работать» с чёрным
экраном — `info status` при этом врёт про `running`. Проверять надо снимком
экрана, а не статусом.

## Дальше

1. Найти условие, по которому книга решает, что файла нет: теперь есть и
   трассировка, и исходники — сопоставить.
2. Разобраться с конкатенацией строк: сообщение собирается не полностью.
3. Умолчания свойств — по-прежнему главный кандидат в первопричины.
