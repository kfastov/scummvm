# 0042 — Формат сжатия прочитан по компрессору, но куски 2..N не находятся

**Дата:** 2026-08-13
**Статус:** ✅ формат подтверждён кодом, 🔴 раскладка кусков не сошлась
**Тип:** разбор чужого кода

Сегмент 101 в `MTB40BAS.DLL` оказался целиком про это сжатие: по смещению 0 —
распаковщик (0039), а `0xb8`, `0x242` и `0x40c` — **компрессор**. Он и даёт
формат без единой догадки.

## Что говорит компрессор

**`0x40c` — поиск серии.** Сравнивает соседние байты, считает одинаковые и
возвращает вызывающему пару «сколько литералов, какой длины серия». Константы
в коде: `cmp ax, 0f8h` (максимум серии 248), `cmp ax, 0ah` (максимум литералов
10), `cmp ax, 3` (минимум серии 3).

**`0x242` — запись записей.** Байт команды считается прямо:

```
mov al, byte ptr [bp-6]     ; число литералов
sub al, 0bh                 ; == add al, 0f5h  →  команда = count + 0xf5
…
mov al, byte ptr [bp-8]     ; длина серии
sub al, 3                   ; команда = len − 3
```

Она же в начале резервирует два байта под счётчик и в конце их заполняет:

```
mov ax, word ptr es:[bx+12h]      ; запомнить позицию
add word ptr es:[bx+12h], 2       ; пропустить два байта
…
mov ax, word ptr [bp-4]           ; сколько записей вышло
mov word ptr es:[bx+si], ax       ; вписать в зарезервированное место
```

**`0xb8` — нарезка.** Несжатые данные режутся **ровно по 65536 байт**:
`cmp [bp+0ch],1 / ja / jb`, для целого куска `[bp-12h] = 0` (то есть 65536) и
`sbb [bp+0ch],1`, для последнего — остаток.

Итого формат: поток = последовательность кусков, каждый кусок это
`[u16 число записей][записи…]`, каждый кусок разворачивается **ровно в 65536
байт** (последний — в остаток). Серия: команда `c ≤ 0xf5`, длина `c + 3`.
Литералы: команда `c > 0xf5`, число `c − 0xf5`, не больше 10.

Это полностью подтверждает 0030 и 0039 и закрывает вопрос о правиле.

## Что не сошлось

По этому правилу цепочка кусков должна идти подряд. У фона `@0x8a484f`
(640×480, значит 4 куска по 65536 и хвост 45056) находится **ровно один** старт
в окне 800 байт, дающий первый кусок ровно 65536 — `0x8a6c9f`, 9531 запись.
А второго куска нет: перебор всех 65536 позиций после конца первого **не даёт
ни одного** места, где следующий кусок разворачивался бы ровно в 65536.

Значит либо куски лежат не подряд (каждый — отдельный блок кучи, между ними
заголовки и, возможно, промежутки), либо совпадение первого куска случайно и
начало потока найдено неверно.

Проверять это надо не перебором по файлу, а отладчиком: точка останова на
распаковщике (сегмент 101, смещение 0) и чтение его параметров — источник,
приёмник и счётчик — сразу покажет, откуда берётся каждый кусок.
