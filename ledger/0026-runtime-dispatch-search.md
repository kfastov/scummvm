# 0026 — Диспетчер опкодов в 16-битной среде: где его нет

**Дата:** 2026-08-12
**Статус:** ⚠️ частичный результат
**Тип:** разбор чужого кода

Раз имён у байт-кода нет (0024), опкоды остаётся искать в самой среде. Модули с
компакт-диска разобраны как NE и просмотрены на предмет таблиц косвенных
переходов (`2e ff a7` — `jmp word ptr cs:[bx+d16]`), это обычный вид `switch`
у компилятора тех лет.

Найдено во всех модулях:

| модуль | сегментов | крупнейшие таблицы |
|---|---|---|
| `MTB40BAS.DLL` | 190 | 160, 140, 79 |
| `MTB40CMP.DLL` | 44 | **667**, 124, 33 |
| `MTB40RCA.DLL` | 11 | 193, 124, 121 |
| `MTB40RUN.EXE` | 127 | 144, 116, 65 |

**Главная таблица интерпретатора среди них не опознана.** Самая большая в
`MTB40BAS.DLL` (160 веток, сегмент 62) переключается по аргументу функции
(`[bp+0x10]`, диапазон 2…0xa1), а не по байту, вычитанному из потока кода. Все
таблицы, перед которыми есть чтение байта по указателю (`lodsb`, `[si]`, `[bx]`),
мелкие: 74, 70, 58, 25, 16 веток.

Табличных **вызовов** (`2e ff 97`) в `MTB40BAS.DLL` нет вовсе. Значит либо
диспетчеризация идёт дальними указателями (таблица двойных слов), либо цикл
интерпретатора живёт не в `MTB40BAS.DLL`.

Что стоит попробовать в следующий заход: искать таблицы **двойных слов**, где
старшее слово — номер сегмента из таблицы сегментов NE; и отдельно — сегмент,
который вызывается из обработчика сообщений и держит указатель на код
обработчика в кадре стека.

Инструменты: `capstone` в режиме `CS_MODE_16`; среда скопирована в
`games/bashnya/RUNTIME/`, чтобы не монтировать образ каждый раз.
