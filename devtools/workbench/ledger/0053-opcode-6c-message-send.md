# 0053 — Опкод 0x6c: посылка сообщения по имени; найдена цепочка разрешения

**Дата:** 2026-08-13
**Статус:** ✅ разбор операндов подтверждён кодом, ⚠️ порядок обхода не наблюдался
**Тип:** разбор чужого кода

Барьер после исправления builtin 70 (0052) — `opcode 0x6c @0x130579`. Разобран
по машинному коду среды, без единой догадки.

## Инструмент

`tools/ne16.py` (в песочнице сессии, переносится в `tools/` при надобности):
разбор 16-битного NE с **разворачиванием цепочек перемещений**. Это важно: в NE
фиксап записан один раз, а места использования связаны списком — в самом месте
лежит смещение следующего, `0xffff` — конец. Без разворачивания цель дальнего
вызова не находится, и я сперва решил, что перемещения для неё нет.

## Что делает 0x6c

Обработчик — `MTB40RUN.EXE` seg34:0x4960 (таблица опкодов из 0048):

```
mov word ss:[0d9ch], 0
lodsw                    ; операнд u16
add  ax, si              ; цель = адрес СЛЕДУЮЩЕГО байта + операнд
mov  bx, ax
push ss / push 2e86h     ; описатель посылки
lodsb / xor ah,ah / push ax   ; операнд u8 — число аргументов
push ds / push bx        ; дальний указатель на цель
...
lcall seg31:0194h
```

Та же договорённость о смещении, что у 0x6d, — подтверждается.

Вызываемая `seg31:0x0194` заполняет описатель посылки:

* `+6` ← число аргументов;
* `+8` ← **u16, лежащий по цели**;
* `+2/+4` ← указатель на **цель + 2**;
* `+0x42`, `+0x44` ← `MTB40UTL.124(имя, 4)` и `MTB40UTL.124(имя, 8)` — два
  разных хеша имени;
* `+0x22/+0x24` и `+0x12/+0x14` ← два дальних указателя, пришедшие от
  предыдущих инструкций (получатель и контекст: вызов снимает 20 байт, а сам
  0x6c кладёт только 12);
* `+0` ← 1, затем `call seg31:0x1118`.

Значит по цели лежит **`[u16 селектор][имя\0]`** — ровно тот вид, что у 0x6d.

Проверка по книге: инструкция `6c ca 0e 00` при `ip=0x130579` даёт цель
`0x131446`, там `39 9b` + `"myMessage\0"`. Строка `myMessage` встречается в
книге 40 раз, и **префикс всегда `0x9b39`** — значит u16 действительно хеш
имени, а не что-то местное.

## Реализовано

Опкод разбирается и исполняется: селектор и имя читаются, обработчик ищется в
ScriptObject владельца, при `count != 0` (ветка seg31:0x01fb) движок честно
останавливается. Прогон подтверждает разбор:

    ToolBook: сообщение myMessage (селектор 9b39) не разрешено @0x13057a

## Что осталось: порядок обхода

`myMessage` определён в книге **ровно один раз** — в ScriptObject id 130,
а зовут его из id 463. То есть посылка уходит вверх по цепочке объектов.

Цепочка разрешения найдена: `seg31:0x0194` → `seg31:0x1118` → `seg31:0x138c`
(и дальше `seg31:0x1ba6`). Из прочитанного:

* ссылка на объект — пара слов `(handle, класс << 8)`; «пусто» это `(0, 0x0400)`,
  а **конец цепочки зашит константой `(1, 0x0400)`** (`mov [bx+30h],1` /
  `mov [bx+32h],400h`);
* класс берётся как `байт[+0x15] and 0FCh`, семьи по четыре: в коде разбираются
  `0x50/0x54/0x58`, `0x64`, `0x68/0x6c/0x70`;
* `MTB40UTL.50(имя)` возвращает номер системного сообщения (сравнивается с
  `0xffff`, `1`, `0x110`) — то есть у среды есть отдельная таблица встроенных
  сообщений.

Наши два объекта: вызывающий id 463 — `handle=3426, класс 0xc4`; определяющий
id 130 — `handle=001e, класс 0x14`. Ни один не равен корню `(1, 0x0400)`, так
что правило «не нашли у себя — спросить корень» **не подтверждается** и
придумывать его нельзя.

Следующий шаг по методу — не дочитывать 660 байт `0x138c` вслепую, а поставить
точку останова на `seg31:0x138c` в госте и посмотреть, какой объект выбирается
для этой посылки: вопрос о поведении программы решается отладчиком.
