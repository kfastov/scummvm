# 0057 — Пространство номеров свойств подтверждено самой средой

**Дата:** 2026-08-13
**Статус:** ✅ арифметика номера подтверждена, ⚠️ имена по-прежнему под вопросом
**Тип:** уточнение к 0056

Поправка к 0056, где сказано, что гипотеза «номер = 0x4000 + индекс» отклонена.
Отклонена была не арифметика, а **соответствие имён**. Саму арифметику среда
делает сама.

`MTB40BAS.CDBGetValueEx` (ordinal 144, `MTB40BAS.DLL` seg15:0x0bc0) начинается с
неё:

```
cmp  word [bp+0eh], 4288h     ; номер свойства
ja   большие
mov  ax, [bp+0eh]
sub  ax, 4000h                ; ← индекс = номер − 0x4000
jmp  дальше
большие:
mov  ax, [bp+0eh]
add  ah, 70h                  ; для номеров выше 0x4288 сдвиг другой
дальше:
mov  [bp-10h], ax             ; индекс
```

Значит пространство именно такое: **индекс = номер − 0x4000** при
номере ≤ 0x4288, и отдельная ветка выше. Верхняя граница 0x4288 даёт 649
свойств — как раз влезает в таблицу имён компилятора (975 имён).

То есть индексирование таблицы имён по `номер − 0x4000` **не опровергнуто**;
непонятно другое — почему у имён, которые при этом получаются (`abouttoolbook`
для 0x400f, `back` для 0x402e), нет очевидной связи с делом. Возможно, таблица
компилятора хранит не одни свойства и упорядочена иначе; в ней рядом лежит
второй блоб имён и массив пар «смещение, номер», где номера идут не по порядку
массива. Это и надо дочитать.

## Умолчания влияют на результат

Проверено пробой: если несуществующее свойство отдавать нулём вместо пустой
строки, книга записывает в `0x400f` не 12, а 10. Управление при этом идёт тем же
путём, но **значение получается другим**. Значит умолчания CDB нужны не «на
будущее»: без них вычисления книги расходятся с оригиналом уже сейчас. Проба
откачена, движок по-прежнему честно отдаёт пустоту и пишет об этом в лог.
