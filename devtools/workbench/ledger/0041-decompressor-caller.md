# 0041 — Вызывающий распаковщика: куски ровно по 64 КБ выхода

**Дата:** 2026-08-13
**Статус:** ⚠️ разобрано наполовину
**Тип:** разбор чужого кода

Продолжение 0039. Распаковщик (`MTB40BAS.DLL`, сегмент 101, смещение 0) —
целый сегмент под одну функцию длиной `0x4ea`. Кто её зовёт, нашлось не
поиском, а по **таблице перемещений NE**: у каждого сегмента с флагом `0x0100`
в конце данных лежит список фиксапов, и среди них ровно одна внутренняя ссылка
на сегмент 101 — из сегмента 134, смещение `0x14f0`.

Оттуда вызывается **не сам распаковщик**, а функция `0xb8` того же сегмента 101;
она уже дёргает внутреннюю `0x242`, а та — цикл распаковки.

## Что говорит внешняя функция (0xb8)

```
mov  word ptr [bp-4],  8000h        ; шаг 32 КБ
mov  word ptr [bp-0eh],8000h
…
cmp  word ptr [bp+0ch], 1           ; старшее слово 32-битного остатка
ja   ещё_целый_кусок                ; остаток > 64 КБ
jb   последний_кусок
…
ещё_целый_кусок:
mov  word ptr [bp-12h], 0           ; размер куска = 0 ⇒ 65536
sub  word ptr [bp+0ah], 0
sbb  word ptr [bp+0ch], 1           ; остаток −= 65536
…
последний_кусок:
mov  ax, word ptr [bp+0ah]
mov  word ptr [bp-12h], ax          ; размер куска = остаток
```

То есть **выход режется на куски ровно по 65536 байт**, последний — по остатку.
Это прямо подтверждает догадку про 16-битный приёмник: за 64 КБ `rep stosb`
не уходит.

## Что говорит внутренняя (0x242)

Работает с состоянием по указателю `[bp+4]`: поля `+08`, `+0b`, `+0c`, `+0e`,
`+10`, `+12`, `+14`, `+15`. Первое, что делает:

```
mov  ax, word ptr es:[bx+12h]
add  word ptr es:[bx+12h], 2        ; ← сдвиг источника на 2: чтение счётчика
```

— то есть **счётчик записей действительно читается из потока**, как и видно в
самом распаковщике (0039). Дальше идёт вызов `0x40c` с двумя выходными
параметрами и арифметика с `0x80`-добавками к полям `+0b` и `+15` — похоже на
переход к следующему 32-килобайтному куску приёмника.

## Что это уже даёт и чего не хватает

Даёт: **размер куска выхода — 65536**, счётчик записей — из потока, приёмник
меняется между кусками. Значит наша ошибка не в разборе записей, а в том, что
мы склеиваем куски подряд, тогда как оригинал раскладывает их по границам 64 КБ.

Не хватает: что именно делает `0x40c` и как считается адрес источника для
второго и следующих кусков. Проверено и не сошлось: попытка читать счётчик
подряд от найденного начала даёт куски `[65536, 8165, 57371, …]` — первый ровно
64 КБ, дальше рассинхрон, то есть между кусками есть что-то ещё.

Следующий шаг — дочитать `0x242` и `0x40c` до конца.
