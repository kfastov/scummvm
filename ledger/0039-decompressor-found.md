# 0039 — Распаковщик картинок найден в машинном коде среды

**Дата:** 2026-08-13
**Статус:** ✅ алгоритм прочитан из кода
**Тип:** разбор чужого кода

Вместо перебора догадок — поиск самого распаковщика. Признак очевидный:
сравнение с порогом `0xf5` должно быть в коде командой `cmp al, 0xf5`, то есть
байтами `3c f5`. По всем модулям среды таких мест **два**, и одно из них —
`MTB40BAS.DLL` со смещения `0xa5f80`:

```
        lds  si, [bp+0eh]      ; источник
        les  di, [bp+06h]      ; приёмник
        lodsw                  ; ← ЧИСЛО ЗАПИСЕЙ, 16 бит
        mov  bx, ax
        xor  ax, ax
loop:   lodsb                  ; байт команды
        mov  cx, ax
        cmp  al, 0f5h
        ja   literal
        add  cx, 3             ; серия длиной c + 3
        lodsb                  ; значение
        rep  stosb
        dec  bx
        jne  loop
        jmp  done
literal:sub  cx, 0f5h          ; c − 0xf5 литеральных байт
        rep  movsb
        dec  bx
        jne  loop
done:   mov  [bp+0eh], si      ; вернуть указатели вызывающему
        mov  [bp+06h], di
```

## Что это подтверждает и что меняет

**Подтверждает:** длина серии ровно `c + 3`, литералов `c − 0xf5`, никакой
обрезки на конце строки нет — правило из 0030 верно, а из 0021 неверно.

**Меняет главное:** цикл идёт **не до заполнения приёмника, а ровно `BX` раз**,
и `BX` читается из потока первым же словом. То есть поток устроен как
`[u16 число записей][записи…]`, и таких кусков может быть несколько подряд.

Это сразу объясняет «фантомные записи» из 0035: две пары байт, на которых наш
разбор расходился с гостем (`22 05` и `4d 21`), — это **счётчики следующих
кусков**: они съедают два байта и не дают выхода. Расхождение было равно длине
серии, которую мы ошибочно выводили.

**И объясняет полосы.** Приёмник — параметр (`les di, [bp+6]`), и функция
возвращает вызывающему сдвинутые указатели. Значит куски декодируются
**в места, которые выбирает вызывающий**, а не подряд в один буфер. Полосы —
это и есть куски, разложенные вызывающим по своим адресам; наш «линейный» вывод
складывает их подряд.

## Что дальше

Разобрать **вызывающего**: как он считает приёмник для каждого куска. Функция
далёкая (пролог NE `mov ax,ds; nop; inc bp; push bp`), поэтому вызовы идут через
таблицу входов — искать по ординалу среди импортов других модулей, либо ловить
отладчиком: у QEMU есть заглушка GDB (`-s`), и точка останова на этом адресе
покажет параметры прямо в кадре стека.

Проверено по дороге: чтение счётчика само по себе картинку не чинит (у «уровня»
кусок один на 46 070 записей, полосы остаются) — значит дело именно в приёмнике,
а не в разборе потока.
