# Как здесь работать

Проект — запуск двух старых русских игр на маке. «Семь ведьм» (Macromedia
Director 6) уже проходятся; «Башня знаний» (16-битный Asymetrix ToolBook 4.0,
открытых реализаций нет) — в работе, свой движок `engines/toolbook` в ScummVM.

Записи о ходе работы — в `LEDGER.md` и `ledger/`; подробный разбор форматов —
в `NOTES.md`. Ledger дописывается только в конец, задним числом ничего не
правится.

## Метод: что даёт результат, а что нет

Это выведено из практики этого проекта, а не из общих соображений. Список
короткий, потому что разница между пунктами огромная.

### Работает

1. **Отладка живого оригинала.** Эталон в QEMU — не только для сверки картинок.
   * Трассировка блочного слоя (`-trace blk_co_preadv`) показывает, какие куски
     файла программа читает и когда — за минуту отвечает на вопрос «откуда
     грузит», на который перебор гипотез не отвечает часами (ledger/0038).
   * Дамп памяти (`pmemsave`) даёт эталонные байты: сверка нашей распаковки с
     памятью гостя нашла ровно два расхождения на 38 621 запись и сняла
     подозрения с декодера (ledger/0035).
   * Заглушка GDB (`-s`) — точки останова и кадр стека живой программы.
2. **Чтение машинного кода среды.** У игры на диске лежит вся среда ToolBook.
   Поиск характерной константы (`cmp al, 0xf5` = байты `3c f5`) вывел прямо на
   распаковщик картинок за один запрос, и алгоритм прочитан целиком, вместо
   того чтобы угадываться (ledger/0039). Прежде чем гадать о формате — искать
   код, который его разбирает.
3. **Свой инструмент под конкретную задачу.** Когда перебор не влезает в
   Python — маленькая программа на C (`tools/rle/`). Когда нужен воспроизводимый
   обход игры — сценарий ввода в движке. Когда нужно спросить живой движок —
   отладочный мост (`ledger/0013`). Инструмент окупается с первого применения.
4. **Проверка глазами.** Числовые меры («размеры сошлись», «связность выросла»)
   обманывали трижды: правило `c+3` против `c+4` (0025, 0027), куски по 2048
   (0034). Каждый раз картинка расставляла всё по местам за один взгляд.

### Не работает — не тратить на это время

1. **Перебор гипотез по одному лишь файлу данных.** Полосы в картинках: четыре
   версии подряд, все проверены и отпали (ledger/0034), потрачены часы. Ответ
   пришёл из машинного кода за один запрос.
2. **Вывод формата «по согласованности».** Попытка вывести длины операндов
   OpenScript распространением ограничений не сузила ничего (ledger/0023):
   при 180 неизвестных опкодах допустим почти любой разбор.
3. **Доверие числовому совпадению без картинки.** «Выход ровно `rawSize` и вход
   ровно `compSize`» выглядит железным критерием, а на деле в окне 8 КБ даёт
   907 ложных совпадений (ledger/0029).

**Правило по умолчанию:** если вопрос про поведение программы — идти в
отладчик или в её код. Файл с данными отвечает только на вопрос «что лежит»,
и то не всегда.

## Ловушки стенда

Их место — в леджере, вместе с записью, где они всплыли. Самые дорогие:

* **QEMU + `-loadvm`:** набор устройств должен совпадать со снимком, иначе
  «Unknown section or instance 'sb16'». Снимок `bashnya-installed` снят с
  `-audiodev coreaudio -device sb16`.
* **Тип машины:** снимок поднимается только на том же, на котором снят —
  `MACHINE=pc-i440fx-10.1 LOADVM=bashnya-installed ./3-vm.sh run bashnya`.
* **Гостя нельзя перезагружать изнутри** — виснет; перезапускать процесс QEMU.
* **`pmemsave` отдаёт физическую память:** буфер разложен по страницам 4 КБ,
  куски крупнее страницы искать бесполезно.
* **Мышь в госте удваивает сдвиги** — коэффициент в `tools/qmon.py`.
* **Точка останова в QEMU переживает отключение клиента** — снимать `z0` в
  начале и в конце, иначе следующий `Z0` даёт `E22`.
* **Ввод в гостя во время отладки теряется** — клик надёжнее клавиш.
* **Базы сегментов читать сразу после останова**, иначе `DS` уже чужой.
* **Безоконный ScummVM** изредка не поднимается: `4-scummvm.sh` перезапускает,
  но при долгом разборе книги (секунды) проверка «есть ли кадры за 8 секунд»
  срабатывает ложно — запускать движок напрямую.
