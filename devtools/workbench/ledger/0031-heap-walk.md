# 0031 — Куча книги проходится: блок = `[u16 конец][u16 тип][данные]`

**Дата:** 2026-08-13
**Статус:** ✅ структура, ⚠️ пиксели всё ещё не найдены
**Тип:** формат

До сих пор всё в книге искалось перебором и эвристиками. Оказалось, что данные
лежат в обычной **куче с блоками**, и её можно пройти по цепочке.

## Устройство

Блок: `[u16 конец] [u16 тип] [данные]`, где «конец» — смещение **конца блока**
от базы сегмента. База выводится из любого известного блока: например, блок с
DIB занимает `4 + 40 + 1024 = 1068` байт, значит `база = конец_блока − поле`.

Проверено на сегменте с базой `0x1279a05`: цепочка идёт без единого сбоя
тридцать блоков подряд и раскладывается осмысленно —

    @0x1279ce4 тип 0    8 байт   имя "fon"
    @0x1279cec тип 0    1068     DIB 640×480 + палитра
    @0x127a118 тип 0x15 92       свойства объекта
    @0x127a174 тип 0    8        имя "f1"
    @0x127a17c тип 0    1068     DIB 257×328 + палитра
    …далее f2, f3, f4, f5, money_1, money_2, money_3

То есть **объект страницы = имя + DIB с палитрой + запись свойств**, и всё это
идёт подряд. Это и есть настоящая объектная модель — вместо нынешней эвристики
«прямоугольник с координатами, кратными 15» (0028).

Имя хранится блоком `[u32 самоссылка][имя\0]`, что совпадает с прежним разбором
таблицы имён; просто теперь видно, что это тот же общий формат блока, у
которого старшее слово поля равно нулю.

## Пиксели в блоке DIB не лежат

Блок с картинкой ровно `4 + 40 + 1024` байта — заголовок, `BITMAPINFOHEADER` и
палитра. Пикселей там нет.

Проверка по всей книге с верным правилом распаковки (0030): из **2210**
восьмибитных картинок с парой размеров данные лежат сразу за палитрой лишь у
**32** (1%), и **ни у одной** из 221 крупных (распакованный размер больше
64 КБ). Прежние «три годных фона» (0029) были случайностью старого правила
обрезки.

Значит поток пикселей адресуется отдельно и, скорее всего, разрезан на куски
не длиннее сегмента — смещения в куче шестнадцатибитные, сегмент не больше
64 КБ, а `compSize` у фонов доходит до 290 КБ. Это же объясняет «служебные
вставки» из 0021 и разрывы на заставке.

## Что осталось

Найти сегмент с пикселями и связь «объект → его поток». Зацепки: в записи
свойств (тип `0x15`) встречается ссылка вида `14 00 <u16>`; такой же вид у
ссылок в каталоге страниц около `0xb832` и в заголовке книги с `0x18`.

Отдельно проверено и **не подтвердилось**: будто данные заставки начинаются
после строки `ASYM_BeenHere`, которая лежит через 30 байт за палитрой. Разбор с
этого места даёт картинку, сдвинутую на пол-строки; разбор прямо от конца
палитры выровнен верно. Значит либо строка попала внутрь потока случайно, либо
вставка устроена сложнее.
