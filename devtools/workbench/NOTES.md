# Что внутри дисков

Оба образа с трекеров оказались raw-дампами (2352 байта на сектор), macOS их не
монтирует. Конвертер — `tools/raw2iso.py`, результат в `downloaded/iso/`:

```bash
python3 tools/raw2iso.py "downloaded/extracted/Bashnya Znaniy/Bashnya Znaniy.iso" downloaded/iso/bashnya.iso
```

| | Башня знаний | Семь ведьм и заколдованный принц |
|---|---|---|
| Год / издатель | 1996, New Media Generation | 2001, Tivola (рус. — Бука) |
| Движок | Asymetrix **Multimedia ToolBook 4.0** | Macromedia **Director 6** |
| Скрипты | OpenScript (`ButtonClick`, `EnterPage`) | Lingo |
| Данные | `RESOURCE.TBK`, книга внутри `KNTOWER.EXE` с offset 0x29e0 (сигнатура `\x03JBO`) | `Datas/*.DIR`, `*.CST` (RIFX / `MV93`, `MC95`) |
| Исполняемые | **NE, 16-битные** (`KNTOWER.EXE`, `MTB40RUN.EXE`) | PE, 32-битный проектор `Prince.exe` |
| Ассеты | AVI (`BEGIN/`, `DEMO/`), WAV, MIDI | WAV в `sound/`, всё остальное внутри `.DIR` |

## Следствия для портирования

**Семь ведьм** — почти готовый кейс для ScummVM: у него есть движок `director`,
и Tivola-игры на D6 там уже поддерживаются (например `catshats` —
«Hexentanz und Firlefanz», Director 6.02). Нашей игры в
`engines/director/detection_tables.h` нет, то есть путь такой: добавить запись в
таблицу детекта → запустить → чинить то, что вылезет. Это ровно та работа,
которую ScummVM принимает апстримом.

**Башня знаний** — самостоятельный проект. Открытых реализаций ToolBook нет,
формат книги (`.TBK`) и байт-код OpenScript придётся разбирать с нуля. Плюс код
16-битный, то есть ни Wine на ARM, ни Windows 11 ARM его не запустят в принципе —
только эмуляция целого ПК, пока не будет своего интерпретатора.

## Стенд

`3-vm.sh` — QEMU + Windows 98 SE (TCG, Pentium III, Cirrus, SB16, PCnet).
Дистрибутив Windows кладётся в `vm/win98se.iso` — репозиторием не поставляется.

Что выяснилось про гостя, чтобы не наступать второй раз:

- **Сброс внутри процесса QEMU убивает Windows 98.** Перезагрузка из меню Пуск,
  `system_reset` и `loadvm` одинаково приводят к зависанию в реальном режиме на
  заставке (EIP замирает около `0x9dfb`). Свежезапущенный процесс грузится всегда,
  так что перезапуск — это `quit` плюс новый `./3-vm.sh`.
- **USB в госте не установлен**: раздела «Universal Serial Bus controllers» в
  диспетчере устройств нет, поэтому `usb-tablet` для Windows не существует и
  абсолютные координаты через QMP `input-send-event` не доходят. Мышь — только
  штатная PS/2.
- **HMP-команды мыши (`mouse_move`, `mouse_button`) монитор принимает молча, но
  до гостя они не доходят.** Рабочий путь — QMP `input-send-event`.
- **Акселерацию указателя надо выключать**, иначе относительные сдвиги
  домножаются и курсор улетает в угол: `guest-tools/NOACCEL.REG` ставит
  `MouseSpeed=0`. После этого `qmon.py click x,y` попадает в цель с точностью
  в пару пикселей.
- Передача файлов в гостя — через ISO: `hdiutil makehybrid -iso -joliet
  -default-volume-name TOOLS -o vm/tools.iso guest-tools`, диск меняется на ходу
  командой `change ide1-cd0 <путь>` в мониторе.
- ISO нельзя одновременно держать примонтированным в macOS: QEMU не получит на
  него блокировку («Failed to get consistent read lock»). Сначала `hdiutil detach`.

## ScummVM на маке

Своя сборка: `scummvm-src/` (клон апстрима), собрана только с движком `director`
(`./configure --disable-all-engines --enable-engine=director`).

Локальная правка одна — в `backends/modular-backend.cpp`, в `updateScreen()`:
периодический сброс кадра в PNG по ключу `framedump_ms` в конфиге. Она нужна,
чтобы гонять движок без окна и всё-таки видеть картинку: снять экран у хоста
нечем (`screencapture` требует прав на запись экрана), а штатный скриншот
ScummVM висит на нажатии клавиши, которое в безоконном режиме послать некуда.
Значение читается каждый кадр, а не кэшируется: первый `updateScreen` случается
раньше, чем активируется секция игры в конфиге.

Рабочий рецепт безоконного прогона собран в `4-scummvm.sh`. Каждая его часть
обязательна: `SDL_VIDEODRIVER=dummy` убирает окно, `SDL_RENDER_DRIVER=software`
и `SDL_FRAMEBUFFER_ACCELERATION=0` нужны потому, что поверх `dummy` новая SDL
не создаёт рендерер и ScummVM падает с «Parameter 'renderer' is invalid», а
`-g surfacesdl` — потому что OpenGL в этом режиме недоступен.

### Семь ведьм: состояние работ

Сделано:

- **Запись детекта добавлена** (`engines/director/detection_tables.h`): игровой
  идентификатор `sevenwitches`, строка
  `WINGAME1_l("sevenwitches", "", "Prince.exe", "t:0e1975bcf5c000ce3d55e864fc0d8c05", 1851314, Common::RU_RUS, 600)`.
  Цель определяется как `sevenwitches-win-ru`.
- В конфиг обязательно `enable_unsupported_game_warning=false`, иначе ScummVM
  показывает модальное предупреждение и ждёт нажатия кнопки.
- В хук выгрузки кадров добавлена защита: пока экран не инициализирован, снимать
  нечего, и `SDL_BlitSurface` ругается на невалидный `src`. Всплыло это только
  после появления записи детекта — цель стала активной до инициализации графики.

**Значения полей проверки диска** (вытащены из `Prince.exe`, чанки `TXTS`):
`CDName="Tivola"`, `Zielpfad="Datas"`, `suchpfad="Datas:turm"`,
`suchdatei="freu01"`, `startdatei="titel"`, `schreibdatei="hexen.tmp"`.

**Первый рубеж проверки проходит.** Трассировка (`--debugflags=lingoexec -d 5`)
показывает `getNthFileNameInFolder("C:\Datas\turm\", 1) -> FREU01.DIR`, затем
`c_eq` с `freu01.dir` даёт `1`. Ранняя гипотеза про сортировку каталога и
`titel.dir` была ошибочной, обход на её основе откачен.

**Второй рубеж — проверка носителя на запись — разобран и пройден.** Скрипт
создаёт `hexen.tmp` в найденном каталоге: если файл удалось создать и открыть,
значит это винчестер, а не компакт-диск, и `startpath` обнуляется.

Почему не проходило: цикл перебора букв в игре останавливается на **первой**
подошедшей, а в ScummVM подходит любая — значит игра всегда выбирала `C:`, куда
FileIO пускает писать. При этом в движке уже есть соглашение (`xlibs/f/fileio.cpp`):
диск `E:\` изображается доступным только для чтения, «чтобы помочь с проверками
CD во многих играх», а буквы после `E` считаются несуществующими.

Обход (`quirkSevenWitches` в `game-quirks.cpp` плюс поле `_cdDriveLetter`):
`getNthFileNameInFolder` отвечает пустой строкой для всех букв, кроме `E`.
Игра доходит до `E:`, тест на запись честно проваливается, путь остаётся —
проверка диска пройдена целиком. Новых механизмов не заводили, только привели
игру к уже существующему в движке соглашению.

Побочно: `createFile` в FileIO — заглушка (`XOBJSTUB`) с FIXME в коде, а
`FILEIOXT.RAF` движку неизвестен.

**Игра запускается в ScummVM.** Дошли до экрана выбора языка — того же, что и в
виртуалке. Для этого понадобились ещё две правки.

**Ошибка в движке (кандидат в апстрим).** `engines/director/castmember/digitalvideo.cpp`
передавал `_ditheringPalette` в параметр *исходной* палитры `Surface::convertTo`,
хотя это копия текущей палитры игры, то есть приёмник. В 8-битном режиме палитра
приёмника оставалась пустой, и `convertTo` падал с «Unsupported dithering target
format or missing palette» на любом полноцветном кадре видео. Правка выбирает
источник и приёмник по глубине кадра и экрана. Чинит не только эту игру, а любую
с видео в 8-битном режиме.

**Локальная правка для безоконных прогонов.** `SurfaceSdlGraphicsManager::drawMouse()`
роняет движок через `error()`, если экранной поверхности нет, — а под драйвером
`dummy` её и не бывает. Курсор в безоконном прогоне всё равно никто не видит,
поэтому там теперь просто предупреждение и выход. Без этого игра, дойдя до смены
курсора, вставала намертво в отладочной консоли.

**Сценарий ввода для безоконных прогонов.** В `DirectorEngine` нашлось поле
`_injectedEvents`, которое движок вычитывает в `pollEvent`, но никто не заполняет
(им пользуется только тестовый XObject). Через него и сделан ввод: ключ
`inputscript` в конфиге указывает на файл вида

```
# время_мс действие параметры
55000 click 232 215
60000 key 27
```

Время отсчитывается от старта движка, клик разворачивается в три события
(перемещение, нажатие, отпускание). Код — `loadInputScript`/`feedScriptedInput`
в `engines/director/events.cpp`. Это даёт воспроизводимые прогоны: одна и та же
последовательность кликов всегда снимает одни и те же эталонные кадры.

Важная деталь: события кладутся не в `_injectedEvents`, а в сам менеджер событий
через `pushEvent`. Lingo читает положение и кнопки мыши напрямую
(`getMousePos`, `getButtonState`), поэтому события в обход менеджера для игры
просто не существуют. Клик разворачивается в нажатие и отпускание с разносом в
300 мс — Director опрашивает мышь в своём цикле и мгновенный клик не замечает.

**Безоконный режим нестабилен, лечится повтором.** Изредка прогон не поднимается:
лог обрывается после инициализации звука, кадров ноль, ошибок нет — похоже на
гонку при создании поверхностей в драйвере `dummy`. Три места, где ScummVM падал
на отсутствующих поверхностях (`drawMouse`, `clearOverlay`, `internUpdateScreen`),
закрыты защитой, остаток лечится повтором запуска в `4-scummvm.sh`.

Отдельно про таймауты: при фатальной ошибке ScummVM уходит в свою отладочную
консоль и обычный сигнал завершения игнорирует. Убивать только `kill -9` или
`timeout -s KILL` — иначе прогон висит часами. Один такой висел семь часов и
записал 27 тысяч кадров на 5 ГБ.

**Где сейчас упёрлись: заставка не доигрывает до интерактивного кадра.**

Клик доходит до игровой логики (`Movie::resolveScriptEvent(mouseDown)` с верными
координатами), но `spriteId: 0`. Разбор каналов в момент клика (диагностика в
`Score::getMouseSpriteIDFromPos` под `--debugflags=events -d 5`) показал, что в
кадре есть ровно два спрайта: канал 1 — фон во весь экран, канал 2 — пузырь
`(177,94)-(463,378)`. Попадание в пузырь есть, но он не реагирует на мышь, а
каналы 4 и 5 пусты. Кликать было просто не по чему: флаги, которые видны на
экране, нарисованы в картинке пузыря, а интерактивные спрайты в кадр не попали.

Из дампов `Datas/TITEL.DIR` видно устройство заставки: обработчик выхода из кадра
вызывает `Sprich(1, "f001")` (озвучка), затем `startTimer()` и `aktivcursor([4, 5])`,
то есть активирует спрайты флагов; рядом лежит анимация, поднимающая спрайты 4–11
снизу, и кадр-ожидание `if the timer < (2 * 60) then go(the frame)`. Выбор языка
висит на поведенческих скриптах этих спрайтов (`TITEL.DIR-BehaviorScript-53` и
`-59`): они ставят `gSprache` в `"x"` или `"y"`.

Версия про озвучку не подтвердилась: `Sprich` (в `GLOBAL.CST-MovieScript-14`)
ничего не ждёт — ставит путь поиска, вызывает проигрывание файла и возвращается.
Таймер тоже исправен: значения `the timer` растут до 120 и цикл ожидания выходит.

**Настоящая причина: спрайты флагов уезжают за экран.** Прицельный разбор каналов
показал, что спрайты 4–11 в кадре есть и видимы, но их прямоугольники с
отрицательными координатами по вертикали — канал 5 `(138,-237)-(224,-161)`,
канал 6 `(230,-236)-(259,-161)`, канал 4 `(0,-357)-(640,0)`. Флаги улетели выше
верхней кромки, а то, что видно на экране, нарисовано в картинке пузыря.

Механика понятна из связки двух наблюдений. Анимация в `TITEL.DIR` сдвигает
спрайты 4–11 вверх ровно 357 раз (`set the locV of sprite k to the locV of sprite k - 1`).
А трассировка переходов показывает, что после кадра «Sprachwahl» фильм крутит по
кругу кадры 8, 9, 14, 15 и 16 (кадр 16 отработал 637 раз за прогон, остальные по
40–50). То есть кадр с анимацией переигрывается снова и снова, и каждый проход
уносит флаги ещё на 357 пикселей.

**Найдено и исправлено — ошибка в движке.** Замер показал расхождение живых
координат с партитурой: канал 5 стоял на 357 пикселей выше своего места
`(398, 215)`, ровно на одну прогонку анимации, при `_autoPuppet = 2048`.

Бит 2048 — это `kAPLocV`, авто-puppet вертикальной позиции. А в таблице внутри
`Sprite::releaseAutoPuppet` (`engines/director/sprite.cpp`) перечислены `kAPLoc`,
`kAPHeight`, `kAPWidth`, `kAPCast`, цвета и `kAPMoveable`, но **`kAPLocH` и
`kAPLocV` пропущены**. Спрайт, которому меняли позицию по одной оси, не
отпускался никогда, и партитура его больше не восстанавливала. Правка добавляет
обе записи, привязав их к `kSCBStartPoint`, как и `kAPLoc`.

Задевает не только эту игру: страдает любая, двигающая спрайты по одной оси в
зацикленном кадре. Третий кандидат в апстрим за сессию.

После правки спрайты флагов встают на свои места (канал 4 —
`(193,185)-(282,256)`, реагирует на мышь), клик по русскому флагу проходит, и
игра **уходит с экрана выбора языка дальше**.

**Дальше: `getAt` на пустой строке — разобрано и исправлено.**

Трассировка дала цепочку `readFile(...)` → `member(...)` → `value("")` →
`getAt(0, 1)`: игра читала файл настроек, получала пустую строку, `value("")`
возвращал ноль, и `getAt` на нём падал.

Механизм настроек (`GLOBAL.CST-MovieScript-13`, обработчик `prefs`): игра берёт
системный каталог Windows, читает оттуда `hexen.ini`, достаёт путь из второй
строки после «=», и по нему читает `hexen.txt` с состоянием игроков. Обработчик
`Spielstandlesen` умеет обходиться без файла состояния, подставляя шесть строк
нулей, а вот без `hexen.ini` уходит в ветку «повреждение установки».

Понадобились три правки:

1. **`FileIO::m_openFile`, режим 0** был отображён на `append`, хотя в Xtra это
   чтение-запись. Из-за этого открытие отсутствующего файла завершалось успехом,
   чтение давало пустую строку, и собственная ветка игры «файла нет» никогда не
   срабатывала. Теперь режим 0 — чтение.
2. **`FileIO::m_getOSDirectory`** был заглушкой, возвращавшей пустую строку, и
   пути собирались как `\hexen.ini` вместо `C:\WINDOWS\hexen.ini`. Теперь отдаёт
   `C:\WINDOWS` на Windows и `System Folder` на Mac.
3. **Подставной `WINDOWS/hexen.ini`** через штатный механизм `cachedFiles` — так
   же, как уже сделано для `PATH.INI` в играх TKKG и `INSTALL.INF` в PAWS.

После этого игра проходит выбор языка и **доходит до экрана выбора сохранения**
(полка с ботинками) — того же, что и в виртуалке. Ошибок в прогоне нет.

**Итого кандидатов в апстрим за сессию четыре:** палитра приёмника в конвертере
видеокадров, снятие авто-puppet для `locH`/`locV`, режим 0 в `openFile` и
`getOSDirectory`. Плюс два обхода под игру: буква диска для проверки CD и
подставной `hexen.ini`.

**Где стоим сейчас: экран выбора сохранения (полка с ботинками).** Клик по
ботинку не срабатывает. Разбор каналов показал, что попадание есть — канал 9,
`bbox (113,225)-(235,324)`, тест 1, — но `отвечает 0`: движок не считает спрайт
интерактивным. `Sprite::respondsToMouse` признаёт таковым только спрайт с
`_moveable`, кнопку, фильм с включёнными скриптами, спрайт с поведениями (D6) или
со скриптом в партитуре либо на члене каста. У флагов поведение было, у ботинок —
нет, поэтому `the clickOn` равен нулю и кадровый обработчик не понимает, какой
слот выбран. Следующий шаг: найти, чем оригинал помечает эти спрайты
интерактивными (проверить `_behaviors` при загрузке кадра и скрипты членов каста).

## Башня знаний: первый разбор формата

Файлы вынуты с диска в `games/bashnya/`: `KNTOWER.EXE` (38 МБ, книга зашита
внутрь с offset `0x29e0`) и `RESOURCE.TBK` (600 КБ).

Заголовок книги: сигнатура `03 4a 42 4f` — то есть `\x03JBO`, «OBJ» задом наперёд.
Дальше идут восьмибайтовые дескрипторы, а с `0x8fd` — каталог именованных
сегментов, всего двенадцать:

| смещение | сегмент | назначение (предположительно) |
|---|---|---|
| `0x0008fd` | `*ClassTbl*` | таблица классов объектов |
| `0x00093d` | `*ClassEntry*` | записи классов |
| `0x0009af` | `*PTABLE*` | таблица страниц |
| `0x0009ed` | `*WINDOWSEG*` | сегмент окон |
| `0x000a2d` | `*ICONRESTAB*` | таблица иконочных ресурсов |
| `0x000a6f` | `*ICONRESSEG*` | сегмент иконочных ресурсов |
| `0x000ab1` | `*ICONRES*` | сами иконки |
| `0x000b69` | `*OBJTABLE*` | таблица объектов |
| `0x000ba9` | `*IDTABLE*` | таблица идентификаторов |
| `0x000be7` | `*NAMETAB*` | таблица имён |
| `0x001159` | `*RHOTWORD*` | «горячие слова», гиперссылки |
| `0x001199` | `*TbxBase*` | базовый сегмент ToolBook |

**Устройство записи каталога.** Перед именем — четырёхбайтовое возрастающее число
(`0x79`, `0x2e5`, `0x361`, …), после имени с нулевым выравниванием идут пары
шестнадцатибитных значений. Разница между числом до имени и первым после везде
ровно `0x30`, а константа `0x3b` повторяется во всех записях — похоже на тег типа.
Значения маленькие (до `0x391` при файле в 600 КБ), то есть это смещения внутри
таблицы, а не в файле.

**Сегмент скриптов найден: около `0x92198`.** Поиск по токенам OpenScript дал
четыре вхождения `buttonClick`; `enterPage`, `linkTo` и текстовые формы вроде
`to handle` не встречаются вовсе — значит скрипты хранятся не исходником, а в
скомпилированном виде со встроенной таблицей строк.

Гипотеза про разделитель `e0 09 91 5a` **не подтвердилась**: в основной книге на
38 МБ таких последовательностей всего 52, тогда как `buttonClick` встречается 317
раз. Это была особенность ресурсного файла, а не кодировка скриптов.

## Башня знаний: основная книга и байт-код

Настоящая книга зашита в `KNTOWER.EXE` с offset `0x29e0`; извлечена в
`games/bashnya/kntower.tbk` — 38 820 933 байта, та же сигнатура `\x03JBO`, но
**617 именованных сегментов** против двенадцати в ресурсной книге. Базовая
дюжина (`*ClassTbl*` … `*TbxBase*`) лежит с `0x134995`, дальше идут сотни
коротких сегментов вида `*TN*`, `*0U*`.

**Раскладка скриптов** (пример около `0x674dc`): сначала таблица идентификаторов
строками с нуль-терминаторами — `openPopka`, `popka1`, `wait`, `showKristall`,
`playing`, `ButtonClick`, — сразу за ней двоичный код.

**Первая статистика по байт-коду** (область `0x67518`, 4 КБ): операнды почти
всегда отрицательные и кратны четырём — `-4` (82 раза), `-8` (31), `-12` (28),
`-16` (10), `-20` (8). Это характерно для адресации слотов кадра стека с шагом в
4 байта. Байты непосредственно перед таким операндом: `0x02` — 101 раз, `0x0d` —
44, `0x0f` — 14, `0x0c` — 4. То есть `0x02` похож на «положить на стек локальную
переменную по смещению», `0x0d` — на запись.

**Сверка обработчиков.** Три вхождения `ButtonClick` из шести дают после имени
одинаковый заголовок `5f 03 ec 02 29 00 00 00 fc ff … 10 00 18`. Два из них
совпадают **побайтово**: 771 байт после имени и ещё 607 до него, то есть около
1378 байт кода и таблицы идентификаторов идентичны — один и тот же обработчик
скомпилирован в разных объектах. Это удобно: сравнение таких пар отделяет
неизменную часть записи от переменной.

**Маркер границы записи: `2a 00 01 02 01 00`.** Он нашёлся в точке расхождения
двух идентичных блоков и в тех вхождениях `ButtonClick`, что выглядели иначе.
По всей книге таких маркеров 227, медианное расстояние между ними ≈ 2964 байта.

**Ресурсы лежат готовыми BMP.** Сразу за первым маркером идёт сигнатура `42 4d`
(`BM`). Проверка по всей книге: 69 корректных Windows-битмапов (правдоподобные
размеры, нулевые резервные поля, обычный размер заголовка). Пять извлечены в
`games/bashnya/extracted-bmp/` и открываются штатно — первый 37×35, 8 бит.

Практический вывод: **графику из книги можно вынимать напрямую**, свой декодер не
нужен. Для будущего интерпретатора это снимает целый пласт работы — остаётся
логика и разметка объектов.

## tools/tbk.py — разборщик книги

Команды: `extract` (вынуть книгу из `.EXE`), `segments`, `records`, `bitmaps`,
`strings`. На игровой книге: 227 записей, 69 битмапов, каталог из 617 сегментов.

При разборе имён пришлось добавить фильтр: пиксельные данные битмапов дают
длинные цепочки повторяющихся символов, формально проходящие как «печатаемая
строка с нулём». Отсеиваем по разнообразию символов и наличию гласных, а записи
с ресурсом пропускаем целиком.

## Что дал разбор идентификаторов

**Обработчики событий:** `mouseEnter`, `mouseLeave`, `ButtonDown`, `buttonClick`,
`timerNotify`, `mmNotify`, `firstIdle`.

**Логика игры:** `InitGame`, `ResetKristall`, `openPopka`, `showKristall`,
`StartPopka`, `ResetPopka`, `resetHelp`, `helpNumber`, `calcul`, `StopLess`.

**Объекты сцен** — латиницей по-русски: `stol`, `chasi`, `palma`, `solnt`,
`poesd`, `samol`, `priem`, `myles`.

**Главное: мультимедиа идёт через MCI.** В строках лежат готовые команды
Media Control Interface — `wav alias mySound buffer 8 wait`, `play mySound`,
`stop mapMidi wait`, `open`, — а также экранные переходы `vertical split out
speed 2000` и `drip speed 2600`.

Для интерпретатора это ключевой вывод: своего формата у звука и видео нет,
эмулировать надо знакомый строковый интерфейс MCI. Вместе с тем, что графика
лежит готовыми BMP, объём собственного кода заметно сокращается — остаётся
байт-код OpenScript и разметка объектов.

## Строение записи со скриптом

Проверка на записи `0x6acc6`–`0x6b23a` (1396 байт, 30 идентификаторов) опровергла
предположение, будто таблица имён лежит отдельным блоком перед кодом. **Имена
вкраплены в поток команд**: строки идут группами по 2–5 штук, между группами —
участки байт-кода. То есть строки являются встроенными операндами.

**Маркер группы строк: `27 1d 66`.** В книге его 1902 вхождения, и в разобранной
записи он предваряет каждую из шести групп. Следом идёт один меняющийся байт
(`0x45`, `0x26`, `0x20`, `0x2c`, `0x53`, `0x42` — не длина и не счётчик), затем
нуль и сами строки с нуль-терминаторами.

**Резать по маркеру не вышло.** Проверка на записи показала, что `27 1d 66`
предваряет лишь часть групп: операнды вроде `workPath`, `wav\click.wav`,
`openPopka` идут без него. Поэтому в `tbk.py disasm` границы ищутся по
содержимому — печатаемая последовательность с нуль-терминатором, достаточно
длинная и проходящая фильтр осмысленности. После этого запись раскладывается
чисто: куски кода и строковые операнды чередуются.

**Приставка фрагмента кода.** Каждый фрагмент начинается одинаково: ноль, три
двухбайтовых поля, затем байт вроде `0x10`/`0x0e`/`0x18`, три нуля, `fc ff` и
нулевое выравнивание. Похоже на дескриптор обработчика: два поля растут по ходу
записи (смещения), третье меняется скачками (размер?).

Типичный разбор записи `0x6acc6` (обработчики кнопки): код 162 байта →
`popkaRec`, `ResetKristall` → код 67 → `hand`, `mouseEnter` → код 61 →
`default`, `mouseLeave` → код 78 → `workPath`, `wav\click.wav`, `ButtonDown` →
код 114 → `openPopka`, `popka1`, `wait`.

**Проверка полей дескриптора** (запись `0x6acc6`, шесть фрагментов):

| смещение фрагмента | поле A | поле B | поле C | длина |
|---|---|---|---|---|
| 0 | 256 | 258 | 24576 | 162 |
| 185 | 126 | 53 | 72 | 67 |
| 268 | 183 | 47 | 69 | 61 |
| 348 | 234 | 94 | 101 | 78 |
| 460 | 332 | 151 | 151 | 114 |
| 623 | 487 | 863 | 748 | 608 |

Поле A монотонно растёт (126 → 183 → 234 → 332 → 487) и ведёт себя как текущее
смещение; B и C держатся вблизи длины фрагмента. Но точного соответствия нет:
разности A (57, 51, 98, 155) не совпадают ни с длинами фрагментов (67, 61, 78,
114), ни с длинами вместе со строками (83, 80, 112, 163). Значит смещения
считаются в другом пространстве — возможно, без служебных полей или от начала
объекта, а не записи. Оставляю как наблюдение, без натягивания гипотезы.

Заодно подтвердилось, что разбиение на фрагменты верное: сумма длины первого
фрагмента (162) и строк `popkaRec` с `ResetKristall` (9 + 14) в точности даёт
смещение второго фрагмента (185).

## Итог сессии 2026-08-12: инструмент и две игры

### Отладочный мост

Логи как средство диагностики себя исчерпали: прогон растил гигабайтные файлы,
нужный момент приходилось ловить заранее выставленными флагами, а спросить живой
движок было нечем. Поэтому в движок `director` добавлен **мост**
(`engines/director/debug-bridge.{h,cpp}`, ключ конфига `debugbridge_port`):
TCP-порт, одна команда в строке, ответ строкой JSON. Обслуживается из
`pollEvent`, то есть отвечает и когда игра стоит в `go the frame`.

Свои команды: `state`, `sprites`, `hit X Y`, `behaviors CH` (поведения,
экземпляры, спан спрайта и **сырые блоки деталей из файла**), `castinfo`,
`sound`, `shot ПУТЬ`, `event`, `move/down/up/click/drag/key`,
`eval ВЫРАЖЕНИЕ` и `lingo ОПЕРАТОР` — выполнение Lingo без разбора командной
строки, которая съедает кавычки и двоеточия. Всё прочее уходит в штатную
консоль ScummVM (`channels`, `cast`, `var`, `funcs`, `bt`, `disasm`, точки
останова): в `gui/debugger.cpp` добавлен перехват вывода `runCapturedCommand`.

Клиенты: `tools/svmdbg` (командная строка), `tools/svmbridge/mcp_server.py`
(MCP-сервер), общий код в `tools/svmbridge/core.py`. Проводник по игре —
`tools/witches.py`: доводит прогон до нужного экрана по признакам в `state`,
а не по секундам, и умеет обходить все семь локаций со снимками.

### Семь ведьм: игра проходится

Путь целиком: проверка диска → выбор языка → выбор сохранения → заставка →
город → любая из семи локаций → возврат. Три ошибки движка, найденные за
сессию, описаны в леджере 0014, 0017 и 0019.

Отдельно стоит запомнить приём: **сравнение живого состояния с записанным в
файле**. Разбор канала рядом с сырыми байтами блока деталей сразу показал, что
движок держит запись спана от первого кадра, хотя партитура давно указывает на
другую. Ни рассуждением, ни логом это не выявлялось.

### Башня знаний: движок есть, игра — нет

Формат книги размечен (леджер 0015), заведён движок `engines/toolbook`
(леджер 0016): детект, разбор книги прямо из `.EXE`, 51 страница, 2483
картинки, классы объектов, тексты CP1251. Игра не воспроизводится: не разобраны
сжатие картинок и байт-код OpenScript.

Важная поправка к прежнему выводу «графику можно вынимать напрямую»: заголовков
DIB в книге 2484, но несжатыми лежат только те 69, перед которыми стоит файловая
шапка `BM`. У остальных за палитрой идёт свой поток, начинающийся с
`01 00 00 00 01 00 00 00 00 00`. Проверено и отпало: стандартный BI_RLE8
(заполняет 26–284 строки из 480), таблица длин строк (суммы не сходятся),
несжатые пиксели где-то дальше в потоке (корреляция строк со сдвигом на ширину
19% против 76% у заведомо несжатой картинки).

### Управление: две ловушки, на которых легко потерять час

**Клик по городу.** Кликать надо не по картинке дома, а по спрайту-подсветке,
который скрипт кадра подводит под курсор при наведении (`rollOver()` в
обработчике `exitFrame`). Поэтому перед кликом обязательно движение мыши и
пауза на кадр. И точка выбирается не по центру прямоугольника: попадание
считается по маске картинки, а в середине `Ecke` она прозрачна.

**Перетаскивание подарков** живёт в цикле `repeat while the stillDown`, который
водит за курсором спрайт-двойник 120. Отсюда требование к стенду: клик нужно
разворачивать в нажатие, серию перемещений и отпускание, разнесённые во времени
(команда моста `drag`). И отсюда же ошибка 0019: движок пересчитывал
`the clickOn` на каждом обработчике очереди, а первый обработчик к тому моменту
уже подводил двойника под курсор.

## Состояние работ и карта репозитория

**Семь ведьм играются.** Путь целиком: проверка компакт-диска → выбор языка → выбор сохранения →
заставка → город → любая из семи локаций → возврат. Внутри локаций отзываются предметы, подарки
перетаскиваются и вручаются персонажам, озвучка находится и играет. Воспроизводится скриптом
`tools/witches.py` ([0018](ledger/0018-witches-playable.md)).

**И то и другое играется на телефоне.** Pixel 8 Pro, своя сборка APK с теми же
правками ([0020](ledger/0020-android-build.md)): `./6-build-apk.sh` собирает,
`./5-android.sh` ставит и заливает данные обеих игр.

**Башня знаний запускается.** Движок `engines/toolbook`
([0016](ledger/0016-toolbook-engine.md)) проходит старт целиком — проверки
оборудования, таблица результатов, заставки, звук, переходы — и выводит главное
меню, кнопки отзываются ([0084](ledger/0084-game-boots-to-main-menu.md)).
Сжатие картинок разобрано ([0039](ledger/0039-decompressor-found.md)), байт-код
OpenScript исполняется: из 113 встроенных номеров, встречающихся в книге,
разобрано 59 — это 89 % вызовов.

Дальше упирается не в отдельный номер, а в подсистему **наборов** (сборщик
builtin 192 и семейство `Stack*`) — с неё и начинать
([0085](ledger/0085-new-game-hits-collections.md)). Сознательно не сделаны и
обойдены по запасным веткам самой книги: AVI-клипы заставок и зрительные
эффекты переходов ([0084](ledger/0084-game-boots-to-main-menu.md)).

**Кандидатов в апстрим ScummVM: восемь** — [0005](ledger/0005-video-palette-bug.md),
[0006](ledger/0006-autopuppet-locv-bug.md), два из [0007](ledger/0007-fileio-and-ini.md),
[0008](ledger/0008-movie-path-hang.md), [0014](ledger/0014-sprite-span-stale.md),
[0017](ledger/0017-at-path-semantics.md), [0019](ledger/0019-clickon-drag.md).
Ни один не специфичен для этой игры. Патчи не оформлены.

## Башня знаний: состояние после разбора картинок

Сжатие разобрано (леджер 0021): поток — пары «счётчик, значение», счётчик
`c ≤ 0xf5` даёт серию длиной `c+3`, `c > 0xf5` — `c−0xf5` литеральных байт;
серия обрывается на конце строки. Перед заголовком DIB лежит пара размеров,
она же служит критерием при поиске начала данных.

Движок `engines/toolbook` показывает распакованные страницы: заставка
«Программа проверяет настройки компьютера» совпадает с оригиналом в виртуалке.

Что осталось по картинкам: у части изображений несколько строк уезжают вбок —
в потоке есть служебные вставки, которые пока не учтены. Критерий «выход ровно
`rawSize` и вход ровно `compSize`» сходится только у 12 картинок из 500, при
том что размер выхода сходится у 2165 из 2313.

Что осталось по игре: интерпретатора OpenScript нет. Без него нет ни кнопок,
ни переходов, ни мини-игр. Это следующая большая работа.

**Стенд теперь помогает по-настоящему.** Игра установлена в гостя и сохранена
снимком `bashnya-installed`; мышь откалибрована (`MOUSE_SCALE` в `qmon.py`),
клики попадают. Экран гостя — точный эталон 640×480 для сверки распаковки,
а `pmemsave` даёт распакованные буферы (с оговоркой про физические страницы).

## Башня знаний: состояние после разбора скриптов

**Скрипты найдены и нарезаны, но не поняты.** В книге 988 обработчиков
(ledger/0023). У каждого есть таблица строк, и последняя строка в ней — имя
события: `buttonClick`, `mouseEnter`, `mouseLeave`, `ButtonDown`, `EnterPage`,
`timerNotify`, `mciNotify`, `firstIdle`. Двухбайтовые операнды-ссылки
разрешаются в строки этой таблицы, поэтому уже видно, **что** делает
обработчик, хотя ещё не видно, **как**:

    tools/osc.py dis games/bashnya/kntower.tbk --name ResetPage

даёт пятнадцать одинаковых операторов «`prepairButton` от имени `palto`,
`kepka`, `myachik`…» — то есть подготовку предметов на странице.

Команда `tools/osc.py names` строит карту игры без интерпретатора: имена
сообщений (`playStory`, `loadStory`, `ExitGame`, `CallPrice`, `StopPopka`,
`ResetPuzzle`, `movePuzzletoXY`) и литералы (`click.wav`, `noclick.wav`,
`play mySound`, `close mySound wait`, курсоры `hand`/`default`).

**Чего не хватает до игры.** Значения опкодов. Вывести их «по согласованности
разбора» не вышло: ограничение слишком слабое (ledger/0023). Дальше два пути —
разбирать 16-битный `MTB40BAS.DLL`, где лежит диспетчер опкодов, либо набирать
семантику по обработчикам, смысл которых понятен из имён и строк. Плюс к этому
нужна модель объектов страницы (прямоугольники кнопок), которой пока нет.

**Звук и видео своего формата не имеют** (ledger/0024): `WAV/`, `MIDI/`,
`BEGIN/`, `DEMO/`, `END/` с диска скопированы в `games/bashnya/`. Когда
появится интерпретатор, команды MCI из скриптов будут указывать прямо на эти
файлы.

Среда скопирована в `games/bashnya/RUNTIME/` — образ диска монтировать не нужно.

**Среда ToolBook 4.0 лежит на том же диске** — это источник истины по языку:
`tools/osc.py keywords .../MTB40CMP.DLL` печатает 975 имён OpenScript с
номерами. Проверено и отклонено: номера этой таблицы **не** совпадают с
операндами байт-кода.

### Куда двигаться дальше по Башне знаний

По порядку убывания пользы:

1. **Смысл опкодов.** Имён у байт-кода нет нигде: `MTB40BAS.DLL` хранит только
   номера, имена лежат в компиляторе `MTB40CMP.DLL`, и номера этих таблиц не
   совпадают (проверено, ledger/0024). Остаётся разбирать 16-битный код
   `MTB40BAS.DLL` и искать таблицу диспетчеризации опкодов — тогда у каждого
   опкода появится настоящий обработчик, а не догадка.

2. **Оракул через компиляцию, если найдётся точка внедрения.** В таблице имён
   есть `startupAutoScriptFile`, `sysAutoScriptFile`, `SetHandlerScript`. Если
   рантайм умеет выполнить скрипт при старте, можно скомпилировать заведомо
   известный исходник, сохранить книгу и сравнить байт-код — это закрыло бы
   вопрос об опкодах разом. **Не подтверждено:** ключа `AutoScriptFile` в
   строках `MTB40RUN.EXE`/`MTB40BAS.DLL` не видно, и авторская версия ToolBook
   на диск не входит.

3. **Модель объектов страницы.** Без прямоугольников кнопок интерпретатору не
   на чем работать. Записи объектов лежат в основном теле книги; страница
   опознаётся по `ASYM_TpID`, рядом с якорем — имена и фон.

4. **Расхождение по входу в распаковке картинок** (ledger/0025, 0027): с
   поиском начала данных схема сходится точно у 370 картинок из 800, у
   остальных распаковка съедает меньше входа, чем обещает `compSize`. Искать
   служебные вставки в потоке, а не другую длину серии.
